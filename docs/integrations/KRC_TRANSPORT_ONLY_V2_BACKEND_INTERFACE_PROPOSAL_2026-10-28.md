# KRC Research ↔ K_Sentinel Transport Only v2 — proposed backend contract

Date: 2026-10-28. Status: KRC_INTERFACE_PROPOSAL / NOT_DEPLOYED. In response to `kolemasakar/Sentinel-Remote` branch `stage114-transport-only-v2` document `docs/KRC_REQUEST_TRANSPORT_V2_BACKEND_CONTRACT_2026-10-28.md`.

## Boundary
Sentinel owns OIDC, Tailscale, transport HMAC and replay protection, availability, routing and rollback. KRC owns the internal backend, independent authorization of science operations, CriticProfile consent policy, evidentiary semantics and verdicts. Do not embed KRC scientific code or an operation-science policy in Sentinel. Stage114 v1 remains unchanged.

## Endpoint choice
Propose HTTP/1.1 over UNIX domain socket `/run/krc-research-v2/backend.sock`; POST `/v1/execute` and GET `/healthz` for minimal static readiness. Dedicated staging unit under user `krcresearch`, socket access only to a dedicated group that contains the Sentinel transport service identity; enforce SO_PEERCRED and socket mode 0660, root-owned runtime directory as appropriate. Proposed path and account are NOT yet provisioned and may change in coordinated acceptance. Do not reuse 9013, 19014, 19015, 19016, or active Stage114 socket. Requests <= 262144 bytes, responses <= 1048576 bytes; content-type application/json; HTTP method/path allowlist; no provider network by default.

## Request envelope (proposed)
```json
{
  "version": "krc-transport/2",
  "request_id": "stage114-v2-test-0001",
  "operation": "research.profile.validate",
  "identity": {
    "client": "K_Science",
    "principal": "repo:kolemasakar/K_Science:ref:refs/heads/main",
    "repository": "kolemasakar/K_Science",
    "workflow_ref": "kolemasakar/K_Science/.github/workflows/kscience-krc-research.yml@refs/heads/main",
    "transport_verified": true
  },
  "payload": {
    "critic_profile": {
      "profile_id": "synthetic-01",
      "version": "v1",
      "protocol": "KRC Core",
      "topic": "Synthetic test only"
    }
  }
}
```
Identity content is asserted by Sentinel over an independently protected local connection; KRC must bind it to accepted peer credentials and configured service authority, not to untrusted incoming HTTP headers. KRC rejects other clients, unknown operations or version, changed request contents, and unavailable scientific permissions. Approval of CriticProfile cannot be inferred from `transport_verified`.

## Response (proposed)
Success:
```json
{"version":"krc-transport/2","request_id":"stage114-v2-test-0001","status":"completed","result":{"schema":"KRC-CRITICPROFILE-1","validation":"STRUCTURE_VALID","approval_independently_verified":false,"scientific_approval":false}}
```
Scientific REVISE/SHORTFALL is a successful transport response carrying a KRC verdict, not a Sentinel transport failure.
Rejected:
```json
{"version":"krc-transport/2","request_id":"stage114-v2-test-0001","status":"rejected","error":{"code":"OPERATION_DENIED","message":"Request rejected","retryable":false}}
```
Backend unavailable: transport HTTP 503, timeout HTTP 504 when generated by transport, oversize response HTTP 502 or local `RESPONSE_TOO_LARGE` as accepted by transport. Never expose internal exceptions; KRC error codes are versioned. Invalid JSON/schema: 400, auth/peer: 403, unknown/disabled operation: 403, idempotency conflict: 409, rate capacity: 429/503. Exact HTTP mappings require tests and acceptance.

## Deadline, idempotence and cancellation
Propose KRC computation deadline 20 s; Sentinel overall 25 s (ensure upstream transport limits permit), no unbounded queue, return fail-closed on deadline. request_id binds to canonical payload SHA256 + identity/operation. Same id+digest can retrieve stored completion, conflicting digest returns IDEMPOTENCY_CONFLICT. Retention and crash-safe atomic storage must be defined before enabling retries; current Stage114 rejects replay and does NOT implement result replay. No automatic retry of research write/side-effect operation with a new request_id. Cancellation best-effort only and not proof of stopping computation. No background jobs in this interface.

## Failure fixtures
1. success: synthetic profile shape; expect completed and scientific_approval=false
2. science rejected: unapproved/malformed profile; expect rejected INVALID_REQUEST or KRC result REVISE, per published schema
3. backend unavailable: missing socket; Sentinel returns 503 without a new job
4. timeout: stub sleeps >20 s; Sentinel stops waiting, no automatic replay with new request id
5. oversized response: stub emits >1 MiB; transport rejects, no truncation
6. duplicate same request id+hash: require deterministic stored response once idempotence is implemented
7. duplicate id+different digest: IDEMPOTENCY_CONFLICT
8. wrong peer/unknown operation: rejected before invoking science module
9. disabled bibliography network: rejected unless explicitly approved offline injected provider.

## Parallel staging
Yes: build a separate, non-listening or isolated socket staging instance with distinct user/UDS path, SQLite data/state, and test identities, independent of Stage114 v1. No shared ports or durable replay store, no production allowlist change. The existing `src/krc_research/staging_backend114.py` is a PURE IN-PROCESS entrypoint, not a socket. It supports the four operations offline with no-network bibliography default. Its isolated test suite last verified 341/341 PASS (2026-10-25), not a live v2 E2E result.
